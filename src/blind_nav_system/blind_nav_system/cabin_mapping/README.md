# 엘리베이터 캐빈 기록·렌더

`all.pgm`의 좌표계 그대로 캐빈 내부를 추가로 찍는다. slam_toolbox 재개는 불가능하다
(`.posegraph`가 없다). 대신 AMCL이 주는 map 좌표를 앵커로 삼아 `/scan`을 그대로
남기고(`cabin_capture.py`), 격자를 칠하는 일은 전부 오프라인으로 미룬다
(`cabin_render.py`).

**나눈 이유**: 라이브로 칠하면 필터 값(섹터 각도·박스 크기·로그오즈 임계)을
엘리베이터 앞에 서서 고쳐야 한다. 사용자가 현장에 서 있는 시간이 이 작업에서
제일 비싼 자원이다. 캡처는 원본만 남기고, 렌더는 나중에 몇 번이든 다시 돌린다.

## 안전

- `cabin_capture.py`는 **`cmd_vel`을 발행하지 않는다.** 팔·리프트도 명령하지 않고
  `/initialpose`도 쏘지 않는다. 구독만 한다. 이동은 100% 사람(게임패드)이 한다 —
  **기록 전용이라는 것이 이 스크립트의 유일한 안전 근거다.**
- 대시보드(8080)·엘베앱(5000)에 의존하지 않는다. 의존은 `/scan`, `/tf`,
  `/stretch/joint_states` 셋뿐이다.
- `cabin_render.py`는 `all.pgm`/`all.yaml`을 **읽기만** 한다. 출력이 입력과 같은
  경로면 시작하지 않는다.

## 절차

1. **런치는 켜둔 채로 둔다.** AMCL이 살아 있어야 앵커를 얻는다.
2. 게임패드:
   ```
   ros2 run joy joy_node
   ros2 run teleop_twist_joy teleop_node \
       --ros-args --params-file <xbox.config.yaml> \
       -r /cmd_vel:=/stretch/cmd_vel
   ```
   ⛔ **`stretch_gamepad_teleop.py`는 절대 쓰지 마라** — 바디 락을 물어 런치를 죽인다.
3. 로봇을 **엘베 문 앞**(맵에 잘 찍힌 자리)에 두고 기록을 시작한다. 이 순간의
   `map→odom`을 얼리므로 이때 AMCL이 제대로 물려 있어야 한다.
   ```
   python3 cabin_capture.py --out cabin_$(date +%Y%m%d_%H%M%S).jsonl
   ```
   팔이 뻗어 있으면 **시작을 거부한다** — 그 순간의 거부라야 사용자가 팔을 수납하게
   되고, 그게 결과를 바꾼다. (기록 중에 뻗으면 경고만 한다. 거부해도 팔은 안 들어가고
   데이터만 잃는다.)
4. 캐빈 안으로 들어가 **제자리에서 360° 1~2바퀴.** 천천히. 화면이 "너무 빠릅니다"를
   띄우면 그 스캔은 버려진다 — **다음 바퀴에 다시 들어오니 손실이 아니다.**
5. **운영자는 캐빈 밖 '문 옆'에 서서 움직이지 않는다.** 문 정면은 안 된다.
6. `Ctrl+C`로 끝낸다.
7. 렌더:
   ```
   python3 cabin_render.py --input cabin_XXXX.jsonl \
       --map ../../maps/all.yaml --out /tmp/all_with_cabin
   ```
   필터 값이 마음에 안 들면 `--sector-deg`, `--box`, `--box-center`, `--l-occ`,
   `--l-free`를 바꿔 **몇 번이든 다시 돌린다.** 다시 찍을 필요가 없다.

## 설계 근거 (바꾸기 전에 읽을 것)

- **앵커를 얼리는 이유**는 정확도가 아니라 내부 일관성이다. 캐빈은 맵에서 unknown이라
  AMCL이 회전 중 입자가 퍼지거나 열린 문 너머 홀 기하에 잘못 물려 포즈가 점프한다.
  **회전 중 한 번의 점프가 맵 전체를 전단(shear)시킨다.** 실시간 AMCL 포즈도 같이
  기록하므로 "AMCL이 실제로 얼마나 튀었나"는 오프라인에서 공짜로 비교된다
  (`cabin_render.py --use-amcl`).
- **TF는 스캔 타임스탬프로 조회한다.** 최신(`Time()`)으로 조회하면 회전 중 스캔과
  포즈가 어긋나 맵이 통째로 밀린다. TF가 없는 스캔은 **버린다**(보간하지 않는다).
- **`LASER_YAW_OFFSET`(π)을 여기로 베끼지 마라.** 그건 엘베앱이 TF를 안 쓰고 손으로
  맞춘 해킹이다. 이 스크립트는 TF의 `laser` 프레임을 쓰므로 장착 회전이 이미 들어
  있고, 베끼면 정확히 180° 뒤집힌 맵이 나온다. 대신 `pose_base`도 같이 기록해서
  렌더가 '로봇 정면' 섹터를 오프셋 상수 없이 계산한다.
- **각속도 상한 0.30 rad/s**: 번짐 `e = r·ω·t_scan`, `t_scan` 실측 0.122s,
  캐빈 벽 ~0.8m → 격자 절반(2.5cm)을 목표로 하면 ω ≤ 0.25가 권장이고 0.30이 상한이다.
  nav2 `max_vel_theta=0.5`는 정확히 5cm(격자 한 칸)라 마진이 없다.
- **필터 3개는 독립이다.** 섹터(±45°)는 뒤쪽을 빼고, 공간 박스는 각도와 무관하게
  홀·복도·운영자·통행인을 걷어내며, 로그오즈는 한두 장의 튄 관측으로 셀이 뒤집히지
  않게 한다. **박스가 특히 중요하다 — 각도 마스크는 사람 행동에 의존하지만 박스는
  의존하지 않는다.**
- **±45°로 충분한 이유**: 한 바퀴에 임의 방향이 섹터에 머무는 스캔 수
  `N = 2α·f/ω`, α=45°·ω=0.25·f≈7.7Hz → 48장. 점유 판정엔 5~10장이면 충분해
  과충족이고, 남는 여유는 전부 운영자 배제 마진으로 쓴다. ±90°는 커버 이득이 없는데
  안전 마진만 절반으로 깎는다.
- **끝점만 찍지 않고 레이를 따라 free를 칠한다(Bresenham).** 끝점만 찍으면 점선
  윤곽만 생기고 내부가 unknown으로 남아 맵으로 쓸모가 없다.
- **PGM 행 순서**: 이미지 0행 = y 최대. `row = height-1-int((y-origin_y)/res)`.
  여기서 뒤집는 것이 이 작업의 고전적 버그다.
- 기본값은 **원본이 unknown인 셀만** 덮어쓴다. 캐빈은 unknown이라 이것만으로
  충분하고, 좋은 맵 데이터를 이번 기록으로 훼손할 위험이 없다.
  (`--overwrite-known`으로 끌 수 있다.)

## 이 산출물의 지위

**"완성된 맵"이 아니다.** 오늘의 목표는 *캐빈이 이렇게 생겼다*를 눈으로 확인하는
것까지다. nav2에 물리는 것은 별개 판단이다 — 참고로 현재 footprint는 뒤로 0.9m라
실효 여유 요구가 약 1.8×1.35m이고, 캐빈에 맵이 있어도 그대로는 캐빈 안에서 경로가
안 나온다.
