## 1. Nav2 재전송 실패 시 로봇이 멈춘 채 침묵하는 문제 (배치1 · #1) ✅완료

**상황/문제**
시각장애인 탑승자를 안내하던 중 Nav2 목표 재전송이 실패하면, 로봇이 그 자리에 멈춘 채 아무 음성 안내도 나가지 않았다. 사용자는 로봇이 왜 멈췄는지, 다시 움직일지 알 방법이 없었다. 위치: `navigation_client.py`의 `_obstacle_cb` / `_replan_check`.

**분석**
두 콜백이 서로 다른 상황에서 호출된다는 점이 핵심이었다.
- `_replan_check`: 이미 `cancel` 이후에만 호출되는 경로 — 실패 시 바로 `_nav_failed` 처리해도 안전.
- `_obstacle_cb`: `cancel` 없이도 발생하는 **의도된 preempt(재계획)** 경로 — 여기서 무조건 `_nav_failed`를 태우면, 정상적으로 재계획 중인 주행까지 "실패"로 오판해 잘못된 실패 안내가 나갈 위험이 있었다.

**결정**
(d)안 채택: `goal_handle is None`일 때만 `_nav_failed` 처리. `goal_handle`이 살아있으면 로그만 남기고 정상 주행을 유지한다.

**변경**
- `_nav_failed`에 `get_logger().error()` 추가 → `/rosout` → `robot_diag_nav`로 실패 이력이 영속화되도록 함
- `start_navigation`에서 서버 대기를 1회만 수행, `_send_to_nav2`는 `server_is_ready()`로 논블로킹 처리
- goal generation 번호로 낡은(stale) 콜백을 필터링
- 재진입 방지 플래그 `_failed_announced`를 `start_navigation`에서 리셋 (실패 안내가 다음 주행에도 눌어붙는 것 방지)

**결과/근거**
verifier 최종 검증 통과. 배치1 ✅완료 (FINDINGS.md 참조).

## 2. 로그 계측 공백 해결 — 동기 line-buffer vs 비동기 큐 (배치A · #15, 진행 중)

**상황/문제**
대시보드 로그(`main._log()`)가 메모리 전용 ringbuffer(maxlen=800)에만 쌓여 파일로 전혀 남지 않았다. 대시보드가 크래시하거나 kill되면 직전 로그가 그대로 증발 — #11(좀비 프로세스), #12(자식 프로세스 방치), #17(주행 중 반복 정지)처럼 "왜 멈췄는지"가 가장 궁금한 순간의 증거가 사라지는 구조였다.

**분석**

## 8. 두 프로세스 병합 대신 제어권 계약을 고친 결정

**상황/문제**
대시보드(:8080)와 엘베앱(:5000)은 별도 프로세스로 떠서 HTTP로 제어권(authority)을 주고받는다. 엘베 시나리오 도중 카메라가 안 켜지거나 두 프로세스가 서로 교착하는 일이 반복됐고, 사용자가 "두 `main.py`를 하나로 합치면 해결되지 않겠냐"고 제안했다.

**분석**
교착의 진짜 원인을 코드에서 확인: 엘베앱 부팅 시 `http://localhost:8080/battery_status`를 **1초 타임아웃**으로 딱 한 번 찔러보고, 그 결과만으로 제어권을 정한다(`elevator_button_press/main.py:3887-3898`). 이 판단이 부팅 시점 단 한 번뿐이고 이후 재동기화가 없다 — 코드 자체에 "★가설②: probe가 늦어 timeout되면 대시보드가 살아있어도 단독모드로 오판 → Nav2와 cmd_vel 경합으로 이동이 막힐 수 있음"이라는 자기 경고 주석이 이미 달려 있다(**확증**, 직접 읽음). 대시보드가 재시작되면 두 프로세스의 "누가 주도권을 가졌는가" 인식이 어긋나는 스플릿브레인이 발생하고, 이때 양쪽이 동시에 `cmd_vel`을 쥐는 것이 문제의 실체다. #11(대시보드 두 번 실행 → 좀비)·#12(크래시 시 자식 방치)가 같은 뿌리(C: 프로세스 생명주기)에서 나온 증상이다.

병합했을 때 잃는 것도 실측 근거로 계상했다:
- **(a) 커널 수준 강제정지 상실**: 엘베앱이 먹통일 때 쓰는 `pkill`(OS SIGKILL)은 프로세스 경계가 있어야 가능한 최후 백스톱이다. 파이썬은 스레드를 강제 종료할 수 없어, 병합하면 #9(취소 시 팔 뻗은 채 고착)에 대한 이 백스톱이 사라진다.
- **(b) 자원 경합 확대**: nav·엘베 콜백이 단일 executor를 공유하게 되면, 기존에 관측된 "nav+엘베 동시 운영 = 838 드롭"([[nav-elevator-overload]] 메모리) 현상이 구조적으로 상시화될 위험.
- 반면 TF OCR은 **이미 별도 venv로 격리**되어 있음을 확인(**확증**, `elevator_button_press/` 내 venv 참조 다수 — `visual_servo_node.py`, `elevator_node.py` 등) — "OCR 크래시가 대시보드를 함께 죽인다"는 걱정은 현재 구조에서 기우.
- DDS 참가자 수가 2→1로 주는 것은 병합의 실질적 이득으로 정직하게 인정.

**결정**
프로세스 병합은 하지 않는다. 대신 **제어 모델만 통합** — 하나의 오케(대시보드)가 nav·엘베를 peer로 명령하는 계약으로 만들고, **프로세스는 분리 유지**한다.

**변경(계획, 미착수)**
- 부팅 시 1초 HTTP 추측 대신, `--managed` 플래그로 제어권을 명시적으로 부여 + 이후 재동기화 로직 추가 (~20줄 규모) — 배치C에 포함 예정
- 사용자 대면 UI는 iframe으로 통합(백엔드 코드 변경 0줄)
- "진짜 프로세스 병합"은 배치C 이후에도 문제가 남으면 그때 재판단

**결과/근거**
오케(명령 통합)와 프로세스분리(커널 SIGKILL 보장)는 서로 배타적이지 않다 — "경계를 지우는 것보다 정직하게 만드는 것이 싸고 안전하다"(kill 능력·자원 격리 보존). **상태: 결정됨, 구현은 배치C 대기.**

1. **제어권 전환 아님** — 엘베앱 `nodes=2`가 `authority=False`/`True` 양쪽에서 동일. 처음부터 고립 상태였다(사용자의 원래 가설이었으나 데이터가 반증).
2. **env 발산 아님** — 엘베앱·인터페이스·런치노드의 `/proc/PID/environ`이 `FASTRTPS_DEFAULT_PROFILES_FILE`·`ROS_DOMAIN_ID`·`RMW`·`LOCALHOST_ONLY` 전부 동일. verifier가 이전에 "프로파일 발산 아니다"라고 판단했던 것이 실측으로 확증됨.
3. **venv 버전 아님** — 엘베앱 venv가 `include-system-site-packages=true`라 시스템 FastDDS 2.6.10을 그대로 쓴다(자체 rmw/fastdds 없음).
4. **SHM 아님** — `shm=0`, `/dev/shm/fastrtps` 잔재 없음.

네 가지가 전부 반증되면서, 남은 유력 후보로 **"단일 머신인데 노드 디스커버리가 WiFi UDP 멀티캐스트를 타고 있다"**가 떠올랐다. `fastdds_no_shm.xml`(SHM 회피를 위해 도입됨, [[fastdds-no-shm]])이 `useBuiltinTransports=false`+UDP 전용이라 디스커버리가 멀티캐스트로 나가는데, 이 세션이 `ip -brief link show`로 직접 확인한 결과 이더넷(`enp86s0`)은 DOWN, WiFi(`wlo1`)만 UP이었다(**확증**) — `ROS_LOCALHOST_ONLY=0`이면 이 멀티캐스트가 WiFi 인터페이스를 통해 나가고, WiFi 멀티캐스트는 DDS 디스커버리에 본질적으로 불안정해 참가자별 간헐적 고립을 일으킬 수 있다. `IgnoredMulti`·`RcvbufErrors`가 0이 아닌 것이 그 흔적으로 관측됨(카운터 절대값은 세션마다 리셋돼 비교 무의미하나, 0이 아니라는 사실 자체는 이 세션이 재확인).

**결정**
**새 K0 = 모든 ROS 노드가 물리적으로 한 대의 머신에서 도는 것을 이용해 `ROS_LOCALHOST_ONLY=1`로 loopback을 강제한다** — WiFi 멀티캐스트 의존을 아예 제거하면서, SHM 회피(`no_shm` 유지)도 그대로 지킨다. **미증명** — 다음 세션에서 엘베앱을 `ROS_LOCALHOST_ONLY=1`로 재기동해 고립이 사라지는지 실험 필요.

**주의(caveat, 사용자 확인 필요)**: `ROS_LOCALHOST_ONLY=1`은 원격(다른 PC)에서 이 로봇의 ROS 그래프를 봐야 하는 경우 못 쓴다 — 현재 RViz도 로봇 로컬에서 띄우고 있어 아마 안전하지만, 사용자에게 원격 접근 필요 여부를 확인해야 확정할 수 있다.

## 20. 엘베 캐빈 맵핑 — 기각 판정 (사용자 질문에 대한 답)

**상황/문제**
사용자가 "엘베 캐빈만 따로 지도에 넣으면 어떤가"를 물었고, 같은 날 팀이 "층 맵 병합" 아이디어는 기각한 바 있어 둘을 사용자가 같은 것으로 오해할 수 있는 상황 — **먼저 구분**: 사용자 아이디어(캐빈 전용 맵)와 오늘 기각한 것(층 맵 병합)은 **다른 것, 충돌 아님.**

**분석 — 기각 권고 근거 3층(advisor)**
1. **개루프 실측 오차가 이미 작다**: #92 리플레이 4건 기준 186cm 중 오차 최대 2cm(1.1%) — 맵핑으로 더 줄일 여지가 거의 없다.
2. **nav2 footprint가 이미 캐빈을 다 삼킨다**: `nav2_params_human.yaml`의 footprint가 `[[0.175,-0.175],[0.175,0.475],[-0.9,0.475],[-0.9,-0.175]]`(뒤로 0.9m 확장, 사람을 몸으로 처리하려는 의도적 설계)에 `footprint_padding=0.08` + `inflation_radius` 0.35(local)/0.55(global)까지 얹으면(**확증**, 이 세션이 yaml L196-197·203-204·246·275-276 직접 대조) **캐빈 크기 자체가 이 확장 풋프린트보다 작아 캐빈 전체가 사실상 lethal(장애물) 판정**을 받는다 — 맵을 정확히 그려도 nav2가 그 안에서 계획을 세울 여지가 없다.
3. **측위 스택이 싱글턴**: `map_server`·AMCL·TF가 시스템에 하나뿐이라, 캐빈만 "AMCL로" 측위하려면 두 번째 측위 스택 + 커스텀 TF 트리가 통째로 필요 — 캐빈 하나 위해 들이기엔 과함.

**SLAM 경로도 별도로 막혀 있음(확증)**
`navigation-and-slam-guide.md` L41-42(**확증**, 이 세션이 직접 grep) — 가이드가 지시하는 SLAM 실행 인자 `min_laser_range:=0.8`이 캐빈 벽(0.7~1.0m 거리)을 통째로 버린다. 하드웨어 문제가 아니다 — `/scan`의 실제 `range_min`은 0.15, `range_max`는 12.0(오케 라이브 파라미터 조회, **정황**)이라 라이다 자체는 그 거리를 볼 수 있는데 SLAM 실행 인자가 스스로 잘라내는 것. 같은 가이드의 `minimum_travel_distance:=0.1`도 이동량이 작은 캐빈 안에서는 스캔이 잘 안 쌓이는 조건이라, **캐빈 안에서는 SLAM이 사실상 스캔 1장으로 퇴화**한다.

**결정**
캐빈 맵핑은 기각. 대신 폐루프 대안(advisor 제안, 오늘 착수 안 함): 후방 여유(라이다로 잰 뒤쪽까지 거리)는 층마다 홀 건너편 벽까지 거리가 달라 기준으로 못 쓴다 — 대신 **측벽이 사라지는 순간**(캐빈 벽 반사가 안 잡히기 시작하는 지점)이 "문틀을 벗어났는가"를 직접 재는 신호가 될 수 있다. 맵도 AMCL도 필요 없는 설계. **오늘 할 일 아님** — 지금은 #92의 `scene_acc` 진행량 게이트로 충분하다는 판단.

**재매핑 자체의 필요성도 낮음**: `all.pgm`이 3월 20일자로 오래됐지만, 측위 실패나 AMCL 발산의 로그 증거가 없다(정황 부재 확인). 유일하게 근거 있는 트리거는 FINDINGS #93("1~4층에서 5층 맵으로 실제 측위가 되는가") — 이건 한 층 주행 1회로 끝나는 확인이라 그쪽이 우선.

**결과**
기각 확정(캐빈 전용 맵/측위 스택 신설 안 함). SLAM 대안도 안 함(min_laser_range 재설정 자체가 캐빈 벽 반사 노이즈를 다시 불러들일 위험이 있어 별도 검토 필요, 미착수). 측벽-소실 기반 폐루프 대안은 아이디어 단계로 보류.

**상태: 기각 판정 완료(설계 결정). 실행 항목 없음 — FINDINGS #93(1~4층 측위) 확인이 관련 후속 중 우선순위.**
